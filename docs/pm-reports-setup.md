# PM และตรวจรับใน MEMs

อัปเดต 4 พฤศจิกายน 2569: กรอก บันทึก และสร้าง PDF/พิมพ์ใน MEMs โดยตรง ไม่ต้องเชื่อม Apps Script หรือส่งคำตอบไป Google Forms

## การใช้งาน

1. แอดมินเปิดฟังก์ชันที่เมนู PM/ตรวจรับ → ตั้งค่าฟังก์ชัน และให้สิทธิ์ `pm_reports` ในหน้าจัดการบัญชีเดิม
2. เลือก PM หรือ ตรวจรับ วันที่ ผู้ปฏิบัติงาน และหน่วยงานเริ่มต้นจากดรอปดาวน์ที่ใช้รายชื่อหลักร่วมกับหน้าเตรียมเครื่อง และรวมหน่วยงานเพิ่มเติมที่เคยบันทึกในระบบ เลือกหน่วยงานรายเครื่องต่างจากค่าเริ่มต้นได้
3. เลือกรายชื่อผู้ปฏิบัติงานที่เคยบันทึกไว้ หรือกรอกชื่อและตำแหน่งแล้วกด “บันทึกชื่อและตำแหน่งไว้ใช้ครั้งต่อไป” รายชื่อใช้ร่วมกันเฉพาะผู้มีสิทธิ์ PM/ตรวจรับ ไม่ใช่การสร้างบัญชีเข้า MEMs ตำแหน่งเก็บกับรายงานและแสดงใน PDF โดยไม่เปลี่ยนประวัติเดิม
4. เพิ่มเครื่องได้ 1–50 เครื่องต่อชุด รวมหลายประเภทได้ ระบุประเภทคู่กับ **No. หรือ S/N** อย่างใดอย่างหนึ่ง แต่ละเครื่องมีหน่วยงาน ยี่ห้อ รุ่น ผลตรวจ และหมายเหตุแยกกัน
5. No. / S/N ที่ตรงทะเบียนหนึ่งรายการจะเชื่อมทะเบียนให้อัตโนมัติ ไม่บังคับ ID/เลขครุภัณฑ์ หากไม่พบทะเบียนให้กรอกรายละเอียดเครื่องเพื่อบันทึกรายงานได้ทั้ง PM และตรวจรับ โดยการตรวจรับใหม่ของศูนย์เครื่องมือแพทย์จะเพิ่มทะเบียนพร้อมบันทึกหากผู้ใช้มีสิทธิ์จัดการเครื่องมือ ส่วน PM หรือหน่วยงานอื่นบันทึกเฉพาะรายงาน หากพบทะเบียนซ้ำจะไม่เดาว่าเป็นเครื่องใด
6. ปุ่ม “เพิ่มหลายหมายเลข” ใช้ No. คั่นด้วยจุลภาค/เว้นวรรค หรือ S/N หนึ่งเครื่องต่อบรรทัด ปุ่มใช้รายละเอียดกับเครื่องประเภทเดียวกันคัดลอกเฉพาะยี่ห้อ รุ่น ชนิดเครื่อง และหน่วยงาน ไม่คัดลอกผลตรวจ หมายเหตุ หรือ S/N
7. เลือกผลตรวจครบทุกข้อ ไม่มีการเลือกผ่านอัตโนมัติ เฉพาะผลไม่ผ่านต้องกรอกหมายเหตุรายเครื่อง ส่วน N/A บันทึกได้โดยไม่ต้องใส่เหตุผล
8. ตรวจทาน ยืนยันผลจริง และกดบันทึกทั้งชุด ถ้ารายการใดผิดพลาดจะไม่บันทึกทั้งชุด
9. กด PDF/พิมพ์ทั้งชุดหลังบันทึก หรือค้นจากประวัติแล้วเลือกพิมพ์รายเครื่อง/รายการที่เลือก/ทั้งชุด

## PDF

อ้างอิงโครงแบบ Slides เดิม: PM สีเขียว ตรวจรับสีฟ้า มีชื่อโรงพยาบาล ชื่อและโลโก้ MEMs ข้อมูลเครื่อง ตารางตรวจ หมายเหตุ ผู้ตรวจ และวันที่

- ใบปกติหนึ่งเครื่องต่อหน้า A4; ข้อความยาวต่อหน้าโดยไม่ตัดทิ้ง มีรหัสเครื่องและเลขหน้ากำกับ
- ใช้ snapshot ณ วันบันทึก ไม่เปลี่ยนตามทะเบียนที่แก้ภายหลัง
- ใบ PDF มีชื่อผู้ตรวจและช่องลงนามจริง ไม่ใช่ลายเซ็นอิเล็กทรอนิกส์
- หากสร้างไฟล์ไม่สำเร็จ สร้างซ้ำจากประวัติได้ ไม่ต้องบันทึกการตรวจซ้ำ
- ไม่จำเป็นต้องสร้างสำเนา Slides/อัปโหลด Drive ทุกครั้ง
- ประวัติเดิมยังอ่านและพิมพ์ได้ ลิงก์ Slides/PDF เดิมยังเปิดได้ ไม่ลบ Forms, Sheets, Slides หรือข้อมูลต้นฉบับ

## โครงสร้างและนำขึ้นระบบ

ใช้ migrations PM เดิมสองไฟล์ และ `20261104040109_pm_native_batch_reports.sql` เพิ่มตารางชุดงานและ RPC `save_mems_report_batch` เป็น SECURITY INVOKER ใช้สิทธิ์/RLS เดิม พร้อม guard ตรวจข้อมูลรายเครื่อง และ deferred constraint trigger บังคับชุดงานครบและไม่มีเครื่องซ้ำ

- RPC หนึ่งคำขอ = transaction เดียว รายการในชุดอ้างอิง parent payload และตำแหน่งของตัวเอง
- UUID ชุดงาน/รายงานคงเดิมขณะลองซ้ำ ล็อกชุดงานป้องกันคำขอพร้อมกัน
- หากเครือข่ายหลุดและยังยืนยันผลไม่ได้ UI ล็อก payload ไว้ให้กดลองชุดเดิมจนยืนยันผลสำเร็จ ไม่มีการแก้ payload แล้วส่ง UUID เดิม
- ลูกข่ายไม่มีสิทธิ์แก้/ลบชุดงานหรือประวัติที่บันทึกแล้ว
- ฟังก์ชัน/ประวัติเดิมอยู่ต่อ ไม่เพิ่มสิทธิ์ผู้ใช้หรือเปลี่ยนสวิตช์ฟังก์ชันโดยอัตโนมัติ
- `gas/pm-reports/` และ Edge Function export เดิมเก็บเพื่ออ้างอิงประวัติ หน้าใหม่ไม่เรียกใช้
- ต้อง apply migration ก่อนเผยแพร่ frontend ชุดใหม่

## รายชื่อผู้ปฏิบัติงานและตำแหน่ง

ใช้ migration `20261104042536_pm_saved_operators.sql` ก่อน frontend รุ่น operators เพิ่มตาราง `mems_report_operators` ที่มี RLS และ RPC `save_mems_report_operator` ชื่อ+ตำแหน่งซ้ำจะได้รายการเดิม ผู้มีสิทธิ์เพิ่มและอ่านรายชื่อได้ แต่ไม่มีสิทธิ์แก้/ลบรายชื่อหรือตำแหน่งย้อนหลัง ตำแหน่งที่กรอกในชุดงานเก็บไว้ใน payload และ snapshot ของรายงาน ไม่ดึงตำแหน่งปัจจุบันจากรายชื่อมาเขียนทับรายงานเก่า

## รายชื่อเครื่องและประเภทเครื่องบนรายงาน

- ช่อง “ชื่อเครื่องจากทะเบียน MEMs” เป็น select จาก `assets.type` และช่อง No./S/N เป็น select ของประเภทนั้นจากทะเบียนล่าสุด ไม่ใช้รายการหมายเลขของเครื่องชนิดอื่น
- เครื่องรับใหม่เลือก “เครื่องใหม่ที่ยังไม่มีในทะเบียน” แล้วกรอกชื่อและหมายเลขเองได้ การตรวจรับของศูนย์เครื่องมือแพทย์สามารถเพิ่มทะเบียนพร้อมบันทึกได้ตามสิทธิ์จัดการเครื่องมือ
- “ประเภทเครื่องบนรายงาน” เป็นรายการที่เก็บใน `mems_report_tool_types` เพิ่มชื่อใหม่ด้วยปุ่มข้างช่อง และบันทึกผ่าน RPC `save_mems_report_tool_type` เพื่อเลือกใช้ครั้งต่อไปได้
- Migration `20261104043729_pm_tool_type_catalog.sql` นำเข้าชื่อที่ตรวจพบใน **คอลัมน์ D ของตารางคำตอบ Google Form เดิมทั้งสองแบบ** รวมตัวสะกดที่ซ้ำกัน และไม่นำค่าทดลองอย่าง “123” หรือ “ทดสอบ” มาเป็นประเภทเครื่อง
- ชุดเริ่มต้นนี้ไม่ใช่รายการ choices ทั้งหมดที่อ่านจากโครงสร้าง Form โดยตรง เนื่องจากการเชื่อมต่อยังอ่าน Forms API/หน้าสาธารณะไม่ได้ หากเจ้าของให้รายการตัวเลือกจริงเพิ่มเติม ให้นำเข้ารายการเหล่านั้นเพิ่มโดยไม่แก้ข้อมูลรายงานเก่า

## รายการประเภทจาก Form ที่เจ้าของยืนยัน

Migration `20261104044405_pm_confirmed_form_types.sql` เปลี่ยนรายการตั้งต้นเป็น 7 ชื่อตามตัวสะกดที่ผู้ใช้ส่งมา: Defibrillator, Infusionpump, Syringpump, Vital sing Monitor, Electrosurgical, Anesthetic Machine และ Ventilator

รายการเดิมที่คาดจากคำตอบ Form ถูกซ่อนไว้ (ไม่ลบหลักฐานเดิม) ประเภทที่ผู้ใช้เพิ่มเองยังคงอยู่ และสามารถเพิ่มชื่อที่เคยซ่อนกลับมาเป็นรายการผู้ใช้ได้ รายงานเก่าใช้ snapshot เดิมเสมอ

## ยี่ห้อและรุ่นที่เลือกใช้ซ้ำได้

ใช้ migration `20261104063433_pm_saved_brands_models.sql` เพิ่มรายการ `mems_report_brand_models` พร้อม RLS และ RPC `save_mems_report_brand_model` ผู้มีสิทธิ์ PM/ตรวจรับสามารถเพิ่มยี่ห้ออย่างเดียวไว้ก่อน หรือเพิ่มรุ่นคู่ยี่ห้อได้ รุ่นในดรอปดาวน์จะแสดงเฉพาะยี่ห้อที่เลือก เปลี่ยนยี่ห้อแล้วล้างรุ่นเดิมเพื่อไม่เก็บผิดคู่

รายการซ้ำยี่ห้อ+รุ่นจะได้ข้อมูลเดิมโดยไม่สนตัวพิมพ์ใหญ่เล็ก รุ่นชื่อเดียวกันอยู่คนละยี่ห้อได้ นำเข้าคู่ยี่ห้อ/รุ่นที่มีใน snapshot รายงานเดิมเป็นรายการเริ่มต้น โดยไม่แก้ทะเบียนหรือรายงานเดิม ลูกข่ายไม่มีสิทธิ์แก้/ลบรายการย้อนหลัง ยี่ห้อและรุ่นบนใบ PDF ยังคงใช้ snapshot ของการตรวจครั้งนั้น

## คัดลอกผลตรวจไปทุกเครื่องในชุด

เมื่อเพิ่มอย่างน้อยสองเครื่องและกรอกผลของเครื่องต้นทางครบทุกข้อ กด “คัดลอกผลตรวจเครื่องนี้ไปทุกเครื่อง” แล้วกดยืนยัน ระบบจะแทนที่ผลตรวจ พร้อมประเภทเครื่องบนรายงาน ยี่ห้อ และรุ่นของเครื่องอื่นที่เพิ่มไว้ในชุดงานขณะนั้น โดยเครื่องต้นทางต้องเลือกข้อมูลทั้งสามช่องครบ ใช้ได้ทั้ง PM และตรวจรับ รวมทุกประเภทเครื่องในชุดเดียวกัน

ไม่คัดลอกชื่อเครื่องในทะเบียนหรือ No./S/N หน่วยงาน หมายเหตุ หรือวัสดุที่เปลี่ยน ผลตรวจแต่ละเครื่องแก้ต่อได้อย่างอิสระ ต้องตรวจทานและยืนยันผลจริงใหม่ก่อนบันทึก หากเพิ่มเครื่องหลังคัดลอก เครื่องใหม่ยังต้องกรอกหรือกดคัดลอกอีกครั้ง เฉพาะผลไม่ผ่านต้องมีหมายเหตุของแต่ละเครื่อง ส่วน N/A ไม่บังคับเหตุผล

## ตรวจรับเครื่องใหม่เข้าทะเบียนศูนย์เครื่องมือแพทย์

ใช้ migration `20261104081030_pm_acceptance_register_center_assets.sql` ก่อนเผยแพร่ frontend รุ่น acceptance-assets

- เมื่อเลือก **ตรวจรับเครื่องใหม่** และหน่วยงานของเครื่อง (หรือค่าเริ่มต้นเมื่อไม่ได้เลือกแยก) เป็น **ศูนย์เครื่องมือแพทย์** ผู้ที่มีสิทธิ์ `assets`/แอดมินจะเพิ่มเครื่องที่ยังไม่พบในทะเบียนพร้อมบันทึกทั้งชุดใน transaction เดียว
- หน้าตรวจทานแจ้งว่าจะเพิ่มทะเบียนเครื่องใด หลังบันทึกแสดงจำนวนที่เพิ่มและลิงก์จัดการเครื่องมือ
- ไม่แก้สิทธิ์หรือข้าม RLS ผู้มีเฉพาะสิทธิ์ PM ยังบันทึกตรวจรับได้ แต่ไม่เพิ่มทะเบียนจนกว่าจะมีสิทธิ์จัดการเครื่องมือ
- เครื่องที่มีทะเบียนแล้วเชื่อมรายการเดิม ไม่เพิ่มซ้ำ ล็อกตัวระบุของทั้งชุดในลำดับเดียวกัน ป้องกันคำขอซ้ำด้วย UUID ชุดงานเดิม
- No. และ S/N ไม่ตรงกับทะเบียนจะปฏิเสธ ไม่เขียนทับทะเบียนเดิม หากรายการใดผิดพลาดให้ rollback ทั้งรายงานและเครื่องที่เพิ่มใหม่ในชุด
- ผลมี “ไม่ผ่าน” จะลงทะเบียนเป็น “เครื่องยังไม่พร้อมใช้งาน”; หากใช้เฉพาะ S/N ไม่สร้าง No. สมมติ และใช้สถานะ “รอเลขครุภัณฑ์” เมื่อไม่มีผลไม่ผ่าน ส่วนเครื่องที่มี No. และไม่มีผลไม่ผ่านใช้สถานะ “ใช้งานได้”
- ID/เลขครุภัณฑ์ที่ยังไม่มีคงเป็นว่าง ยี่ห้อ รุ่น วันตรวจรับ หมายเหตุ และ UUID รายงานเก็บในหมายเหตุทะเบียน ส่วนรายงานยังเก็บ snapshot แยกเหมือนเดิม
- รายงานเก่าและคำขอลองซ้ำของชุดที่บันทึกไปก่อนหน้าไม่สร้างทะเบียนย้อนหลัง

## ตรวจรับเมื่อมีทะเบียนเดิม

Migration `20261104083953_pm_acceptance_duplicate_confirmation.sql` เพิ่มการยืนยันก่อนเก็บข้อมูลตรวจรับที่ตรงกับทะเบียนเดิม

- No. ตรวจคู่ชื่อเครื่อง/ประเภทในทะเบียน เนื่องจากคนละประเภทใช้ No. เดียวกันได้
- S/N ตรวจในประเภทที่เลือกก่อน หากไม่พบจะค้น S/N ในทะเบียนทั้งหมด ถ้าพบเครื่องเดียวแจ้งชื่อจริงในทะเบียนและผูกข้อมูลตรวจรับกับเครื่องนั้น หากพบหลายเครื่องให้เลือกชื่อเครื่องให้ตรงก่อน
- หน้าตรวจทานแจ้ง “ซ้ำกับเครื่องที่ลงทะเบียนไว้แล้ว” มี “ยกเลิก” และ “เก็บข้อมูลตรวจรับ ไม่เพิ่มทะเบียนซ้ำ” ไม่กดเลือกต่อจะไม่บันทึกรายงาน
- เมื่อยืนยัน เก็บรายงานใหม่ด้วย kind acceptance และ snapshot ของเครื่องเดิม ไม่เพิ่มหรือแก้ assets และยังต้องยืนยันผลตรวจจริงก่อนบันทึกทั้งชุด
- ฐานข้อมูลตรวจ acknowledgement และ ID ทะเบียนอีกครั้ง หากมีคนเพิ่ม/เปลี่ยนทะเบียนระหว่างทำรายการ จะให้ตรวจทานใหม่แทนการเพิ่มซ้ำ กรณี S/N ใหม่ล็อกทั้งตัว S/N และตัวระบุเฉพาะประเภทตามลำดับเดียวกันในทั้งชุด
- ประวัติเก่าและการลอง UUID ชุดเดิมซ้ำยังอ่านผลเดิมได้ตามกติกาเดิม

Migration `20261104085713_pm_na_without_reason.sql` ยกเลิกการบังคับหมายเหตุสำหรับ N/A ทั้ง PM และตรวจรับ แต่ยังบังคับหมายเหตุเมื่อมีผลไม่ผ่าน และยังต้องลงผลให้ครบทุกข้อ/ยืนยันผลจริงก่อนบันทึก
