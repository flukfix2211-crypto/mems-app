# ตรวจและยืนยันการคืนเครื่อง

เมื่อหน่วยงานบันทึกคืน ยังคงบันทึกธุรกรรมคืนและส่ง Telegram ตามเดิม แต่เครื่องเข้าสู่คิว “ตรวจและยืนยันการคืนเครื่อง” ในหน้าเตรียมเครื่อง ไม่ปรากฏในรายการแนะนำพร้อมใช้ และไม่สามารถเตรียม/ส่ง/ยืมได้จนตรวจรับจริง

เจ้าหน้าที่เปิดรายการ ตรวจประเภท/หมายเลข/หน่วยงาน ลงชื่อและติ๊กว่าได้รับเครื่องจริง แล้วกด “ยืนยันการคืนเครื่อง” ระบบบันทึกชื่อ บัญชีผู้ยืนยัน และเวลาจากฐานข้อมูล เมื่อสำเร็จจึงเลือกไปเตรียมได้ตามปกติ ใช้ปุ่มรีเฟรชเพื่อดูรายการคืนใหม่ ไม่ส่ง Telegram ซ้ำตอนตรวจรับ

สิทธิ์ตรวจรับใช้ `prepare` เดิม ทั้ง RPC และ direct table update ต้องผ่าน RLS และ trigger บัญชีหน่วยงานที่มีเพียง `borrow` ยืนยันเองไม่ได้ การตรวจรับเป็นรายการถาวรใน `equipment_return_checks` อ้างอิงธุรกรรมคืน ไม่เปลี่ยนเวลาคืนหรือเพิ่มจำนวนคืนในสถิติ

กรณีเดิมที่เจ้าหน้าที่ได้รับเครื่องจริงแต่หน่วยงานไม่คีย์คืน การยืนยัน “คืนเลย” ก่อนเตรียมยังทำงาน และบันทึกผู้เตรียมเป็นผู้ตรวจรับใน transaction เดียวกัน

## การติดตั้ง

ใช้ migration `supabase/migrations/20261117140000_return_receipt_confirmation.sql` ก่อนเผยแพร่ frontend ชุดนี้ โดยทดสอบกับ staging ของ schema ปัจจุบันก่อน คิวเริ่มเฉพาะธุรกรรมคืนใหม่หลังติดตั้ง ไม่สร้างงานตรวจรับย้อนหลังให้ประวัติเก่า

Migration ใช้ invoker functions, RLS และ machine advisory locks เดิม ไม่เพิ่มสิทธิ์แก้ borrow_records ให้เจ้าหน้าที่ตรวจรับ ตารางใหม่อนุญาต update เฉพาะชื่อ ส่วนบัญชีและเวลายืนยันกำหนดโดย trigger และแก้ลายเซ็นหลังยืนยันไม่ได้

CLI รุ่นล่าสุดใน workspace นี้เริ่มทำงานไม่ได้เพราะ home directory เป็น read-only และรุ่นเก่าดาวน์โหลด binary จาก GitHub ไม่สำเร็จ จึงจัดทำไฟล์ migration โดยตรงและทดสอบ SQL กับ PostgreSQL WASM ในเครื่อง ไม่ได้ apply migration หรือเปลี่ยนฐานข้อมูลจริง

## การตรวจสอบ

- `npm test`: SQL กับ production trigger fixtures รวม pending → signed → prepare, RLS, direct API, ชื่อว่าง, ยืนยันซ้ำ, atomic rollback, legacy และ missing-return flow; dashboard ไม่รวมเครื่องรอตรวจในพร้อมใช้
- `npm run test:returns:browser`: Chromium → local API adapter → PostgreSQL WASM แยก ทดสอบชื่อ/ติ๊กยืนยัน, ยกเลิก, กดซ้ำ, รายการพร้อมใช้หลังยืนยัน และขนาด 390/768/1440 px
- Browser test ตรวจการเรียก notification ตอนยืมและคืนผ่าน shared save function; ไม่ส่ง Telegram จริงและไม่เรียก production

ยังไม่ได้เผยแพร่ frontend หรือใช้ migration ในระบบจริง

## สวิตช์ที่หน้าตั้งค่า

ติดตั้ง migration `20261117150000_return_receipt_setting.sql` เพิ่มเติม ค่าเริ่มต้นเปิดใช้งาน สวิตช์ใช้สิทธิ์แอดมินหลักตาม RLS ของ `app_settings` เดิม เมื่อปิดจะไม่สร้างคิวใหม่และไม่บล็อกเตรียม/ยืม รายการคิวเดิมและลายเซ็นยังเก็บไว้ เมื่อเปิดอีกครั้งรายการที่ยังไม่ตรวจรับจะกลับมาบล็อกเครื่องจนตรวจรับสำเร็จ Telegram ยืม–คืนคงเดิม
