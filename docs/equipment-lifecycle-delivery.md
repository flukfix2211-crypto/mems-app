## พฤติกรรมที่ส่งมอบ

ประเภทและหมายเลขมาจาก assets ใช้คีย์ประเภทที่รวมช่องว่าง/ตัวพิมพ์และ alias ที่ระบุแน่นอนเท่านั้น ไม่มี fuzzy matching ที่อาจจับคนละเครื่อง หมายเลข 01/1.0 ตรงกับหมายเลข 1 แต่เลขเดียวกันต่างประเภทยังคงเป็นคนละเครื่อง เมื่อเพิ่มประเภทใหม่ในทะเบียน หน้าเลือกและสถิติจะอ่านได้โดยไม่เพิ่มรายชื่อรายหน้า

หน้าเตรียมแสดงเฉพาะเครื่องใช้งานได้ที่ไม่มีรอบยืมและไม่มีการเตรียมค้าง เลือกหลายประเภทได้ และคงเหตุผลยกเลิกทั้งสี่ข้อ การยกเลิกตรวจว่าปิดรายการจริงก่อนแจ้งสำเร็จ โหมดเตรียมพร้อมส่งสร้างเตรียมและยืมใน transaction เดียว เชื่อมด้วย borrow_record_id ไม่บันทึกยืมสองรอบ

หน้ายืม/คืนใช้ปุ่มหมายเลขจัดกลุ่มตามประเภทและตึก หลายประเภทในครั้งเดียวได้สูงสุด 5 เครื่อง หรือ Infusion Pump อย่างเดียว 10 เครื่อง การเตรียมธรรมดาไม่ถูกจำกัดไว้ที่ 5 เครื่อง เปลี่ยนตึกหรือโหมดแล้วล้างการเลือก รวม QR หน้าคืนแสดงเฉพาะผู้ถือเครื่องล่าสุดพร้อมวันเริ่มยืมและระยะเวลา High Flow ที่ผู้ถือเครื่องล่าสุดเป็น ER คืนจากตึกใดก็ได้โดยไม่ต้องย้ายก่อน ส่วน ICU และเครื่องประเภทอื่นต้องย้ายตึกก่อนคืนจากตึกอื่น ฟังก์ชันย้ายวอร์ดยังคงใช้ได้ตามสิทธิ์เดิม

ย้ายตึกใช้รอบเดิม ตรวจตึกต้นทางล่าสุดและเก็บ loan_id เดิม Round/Circuit ไม่ปลดสถานะยืม การคืนไม่แก้สถานะซ่อม/ชำรุดในทะเบียนให้เป็นพร้อมใช้

RPC mems_equipment_batch ใช้ SECURITY INVOKER กับ RLS เดิม บันทึกทั้งชุดสำเร็จหรือ rollback ทั้งชุด ล็อกทุกเครื่องตามลำดับเดียวกันก่อนเขียน มี request UUID ป้องกัน replay ซ้ำ และตรวจ cached acknowledgement กับแถวที่บันทึกจริง Trigger บังคับข้อจำกัดแม้เขียนผ่าน table API โดยตรง ฟังก์ชัน audit และ backdate guard เดิมยังอยู่ การแก้เวลายังใช้สิทธิ์เดิมและต้องไม่สลับลำดับธุรกรรมของเครื่อง

เวลา record_date และ record_time ถูกคำนวณจาก recorded_at ใน Asia/Bangkok ฝั่งฐานข้อมูล ไม่ขึ้นกับ timezone เครื่องผู้ใช้ ไม่ได้รวมงานแก้ UI เวลาของแอดมินหลักที่อยู่นอก branch นี้

หน้าสถิติใช้ URL เดิม c2-statistics.html และธีม/ใบ PDF เดิม รองรับทุกประเภท ตัวกรองช่วงวัน ประเภท ตึก และหมายเลข แยกจำนวนเตรียม ครั้งยืม ครั้งคืน รอบปิดสมบูรณ์ และค้างปลายช่วง ชั่วโมงแบ่งตามช่วงถือเครื่องของแต่ละตึกและตัดตามช่วงรายงานจริง รอบเปิดนับถึงเวลาปัจจุบันหรือปลายช่วงแล้วแต่ว่าอะไรถึงก่อน ค่าเฉลี่ยใช้ระยะเต็มของรอบที่คืนในช่วง ณ ตึกปลายทาง ไม่ใช่ค่าเฉลี่ยเฉพาะชั่วโมงที่ตัดในช่วงรายงาน ไม่มีการแปลงจำนวนเครื่องหรือรอบเป็นผู้ป่วย

- `admin_report.html`: ชื่อและคำอธิบายลิงก์รายงานใหม่; `dashboard.html`: เปลี่ยน cache version ของ shared client เท่านั้น
- `tests/fixtures/*`, `tests/lifecycle-sql.test.js`, `tests/equipment-ledger.test.js`, `tests/lifecycle-browser.cjs`: catalog fixture, database/ledger/browser regression tests
- `package.json`, `package-lock.json`, `.gitignore`, `README.md`, เอกสารนี้: คำสั่งทดสอบที่ทำซ้ำได้และขั้นตอนนำขึ้นใช้งาน

## ข้อจำกัดที่ต้องรู้

- ไม่ได้สร้างธุรกรรมทดสอบหรือใช้ migration ในฐานข้อมูลจริง ทุกการเขียนเพื่อทดสอบอยู่ใน PostgreSQL ชั่วคราวที่ลบทิ้ง
- Browser ทดสอบใช้ auth stub และ API adapter ไม่ได้อ้างว่าทดสอบ login/refresh token กับ Supabase จริงครบวงจร นโยบายหลักและ trigger ที่เกี่ยวข้องตรวจจาก catalog จริงและทดสอบในฐานข้อมูลแยก
- QR ทดสอบข้อมูลลิงก์และ keyboard/camera-result handler ไม่ได้ทดสอบกล้องจริงหรืออุปกรณ์สแกนจริง ต้อง smoke test อุปกรณ์จริงใน staging ก่อนเปิดใช้งาน
- ไม่มีการเดาหรือ rewrite ประวัติเก่า รายการยืมซ้อน คืน/ย้ายที่ไม่มีจุดเริ่ม หรือคืนข้ามตึกโดยไม่มีประวัติย้าย แสดงข้อมูลไม่ครบและไม่สร้างชั่วโมง/ยอดค้างที่ยืนยันไม่ได้ สถานะปัจจุบันยังอิงธุรกรรมจริง
- รายการเตรียมพร้อมส่งเก่าที่ไม่มี link ไป prepare_records ถูกแจ้งข้อมูลไม่ครบ ไม่เพิ่มแถวเตรียมย้อนหลังเองเพื่อหลีกเลี่ยงนับซ้ำ
- ค่าเฉลี่ยฐาน “รอบที่คืนในช่วง” ใช้เต็มเวลายืม–คืนของรอบนั้น ชั่วโมงใช้งานในตารางใช้เฉพาะส่วนที่ทับช่วงรายงานและตึกที่เลือก จึงเป็นคนละฐานการคำนวณ
- PostgreSQL ทดสอบ native รุ่น 18; production รุ่น 17.6 จึงควรทดสอบ migration บน staging clone รุ่น 17.6 อีกครั้งก่อน apply จริง
- คำสั่งทดสอบสร้าง/ลบเฉพาะ database ชื่อ mems_test_* หรือ mems_browser_* ต้องใช้ server สำหรับทดสอบที่สร้างฐานข้อมูลได้ ห้ามชี้ไป production

## ขั้นตอนนำขึ้นใช้งานหลังอนุมัติ

1. ตรวจ diff/commit และ PR description แนบ ดูว่า main ยังอยู่ฐานที่ตรวจหรือ rebase ใหม่หากมีงานเข้า ห้ามรวม branch แก้เวลาของแอดมินหลักโดยไม่ทบทวน dependency
2. เตรียม staging clone ของ schema/data ปัจจุบัน โดยไม่ส่งข้อความ Telegram ทดสอบ และสำรอง schema/data พร้อมจุดกู้คืน
3. ตรวจทะเบียนซ้ำด้วยคีย์ mems_type_key(type)+no และเตรียมค้างซ้ำก่อนสร้าง unique index ถ้าพบให้รายงานและแก้ข้อมูลโดยเจ้าของระบบ ไม่ลบ/รวมรายการอัตโนมัติ
4. ใช้ migration ใหม่ไฟล์เดียวกับ schema เดิมใน transaction ทดลองก่อน พร้อมตรวจ advisors/RLS/grants และ audit จริง Repository ยังไม่มี baseline schema เต็ม จึงไม่ควรสมมติว่า supabase db reset จากสาม migration เก่าจะสร้างระบบได้ครบ
5. ทดสอบ staging ทั้งบัญชีที่มีสิทธิ์ บัญชีที่ถูกปิด เครื่องจริง QR กล้อง/สแกนเนอร์ ย้าย ER/ICU และ admin time edit ที่อนุญาต ตรวจว่า Telegram แจ้งเพียงรายการที่บันทึกสำเร็จ
6. หลังอนุมัติการเผยแพร่ แนะนำช่วง maintenance สั้น ๆ ปิดรับรายการใหม่ ใช้ migration แล้วเผยแพร่ commit frontend ชุดเดียวกันพร้อมกัน บังคับ reload/cache version ใหม่ โค้ดเก่าที่ค้างในแท็บอาจไม่ผ่านกติกาใหม่ โดยเฉพาะ deliver แบบเก่า
7. ตรวจ read-only ว่า view แสดง Round/Circuit ไม่ปลดสถานะยืม และตรวจรายการจริงครั้งแรกที่เจ้าหน้าที่ทำตามงานปกติ ไม่สร้างรายการทดลองค้างใน production
8. หากต้องย้อนกลับ ให้หยุดรับรายการและใช้ restore plan ที่ทบทวนกับผู้ดูแลฐานข้อมูล เก็บธุรกรรมที่เกิดหลัง deploy ก่อนกู้คืน ห้าม drop ตาราง/คอลัมน์ใหม่หรือ revert frontend อย่างเดียวขณะระบบเปิดรับรายการ เพราะเงื่อนไขฐานข้อมูลใหม่ยังบังคับอยู่

การเผยแพร่ branch, เปิด PR, apply production migration และ merge ยังต้องรอการอนุมัติขั้นสุดท้ายจากผู้ใช้
